# Study Case
This case study focuses on a Server-Side Request Forgery (SSRF) vulnerability identified in an authorized banking security testing environment.

During the assessment, a server-side request functionality was found to accept user-controlled input and make requests to internal resources. This behavior created a potential SSRF vulnerability because the application could be induced to communicate with services that were not intended to be directly accessible by external users.

Further analysis identified an internal transaction service that did not properly validate the transaction amount. As a result, the SSRF condition could be chained with an improper input validation/business logic flaw, allowing a transaction with a negative amount to be processed in the lab environment.

The scenario demonstrates how vulnerabilities that appear to have limited impact individually can become more serious when chained together.

# Objective

The objectives of this security assessment are to:

* Identify potential Server-Side Request Forgery (SSRF) vulnerabilities.
* Determine whether the application can access internal services on behalf of an external user.
* Assess the security impact of unauthorized access to internal application functionality.
* Identify weaknesses in transaction amount validation.
* Demonstrate the potential impact of vulnerability chaining in an authorized lab environment.
* Provide recommendations to prevent SSRF and invalid financial transactions.
  
# Technical Analysis of SSRF

Server-Side Request Forgery occurs when an application makes a server-side request using attacker-controlled input without adequately restricting the destination.

This can potentially allow an attacker to interact with internal services that are not intended to be directly exposed.

In this scenario:

User → Public Application → SSRF → Internal Service

The security concern is that the application server becomes an intermediary between the external user and internal resources.

Transaction Validation

The internal transaction service should enforce business rules before processing a transaction.

For example, a transaction amount should be validated to ensure that it:

Is present.
Uses the expected numeric format.
Is greater than zero.
Does not exceed applicable transaction limits.
Meets the application's business rules.

The identified weakness indicates that the internal service does not sufficiently enforce these requirements.

# Recommended Remediation
## SSRF Protection
The application should:

* Use an allowlist of approved destinations.
* Restrict server-side requests to required services only.
* Prevent access to unauthorized internal resources.
Apply network-level segmentation.
Validate and normalize request destinations.
Monitor unusual server-side outbound requests.
